The question behind it all

For which kinds of tasks does medium effort do as well as x-high?

the lay of the land

The L1 → L9 ladder

Nine levels of AI-assisted development, from Aleksei Litvinau's course “AI-Assisted Engineering”: alekseilitvinau.com/edu

Ask the room: hands up if you're at L1–L3 (chats), at L4–L5 (an agent in the repo), and who has ever run several agents in parallel. Most teams are at L1–L3 right now. This talk is about what changes at L4–L7, and what I had to build to get there. ~2 min.

why this is possible at all

The whole world is source data

→
Three.jsmeshes, collisions, road graph

What you get

  • Endless content without level designers
  • Something the agent can work with: a standard, well-documented data format

The catch

  • Overpass answers 429 → 30 s timeout, three mirrors, a stale cache as the fallback
  • Dirty data: water 4 m above the river, bridges with no height
The key point for the AI part: agents do best where the data is open and the format is standard. OSM is perfect “content” that nobody has to draw. The same trick later moves over to itffm. ~2 min.

architecture, not agents

OSM + elevation + weather, no server

openstreetmap.orgNominatim, Overpass
AWS Terrain TilesS3, Terrarium PNG
Open-Meteolive weather
→
browserThree.js + IndexedDB, static files on Pages

$0 and zero ops

Nothing to monitor, patch or scale. The CDN takes the load, open APIs serve the data. No infrastructure bill → no need to monetize.

Nothing to leak

No database, no accounts, no secrets. A player's progress stays in their own browser.

Deploy = tag

Rolling back means going to the previous tag. Fork it, and you have your own copy of the game, also for free.

This part isn't about agents, it's about architecture in general. Keyless public APIs with CORS turn the browser into a full client for the whole world's data. You need a server only to store other people's data or to hide keys. Neither applies here. ~2 min.

so that it works instead of falling over

The price: you're a guest on someone else's infrastructure

  • Keyless APIs only. A key in a static site is a public key
  • Respect the usage policy. Nominatim: 1 request per second; Overpass answers 429
  • Caching is mandatory. A city loaded once lives on in IndexedDB
  • Mirrors and timeouts. 3 Overpass mirrors, 30 s, a stale cache as the fallback
  • Honest fallbacks. No terrain → flat ground; no OSM → a procedural forest
  • Attribution. OSM data under ODbL, © OpenStreetMap contributors

And a bonus for agents

No server → no migrations, environments or secrets. You can hand the agent the entire release.

Layer boundaries are written down in AGENTS.md: geo/ knows nothing about Three.js, world/ knows nothing about the network.

The catch of going serverless: your availability is the availability of someone else's free services. Hence the cache, mirrors and fallbacks at every step. The pattern applies far beyond games: dashboards, maps, open-data visualizations. ~2 min.

pace as part of the architecture

A release every ~30 minutes without falling apart

Version = deploy

Every bump is a tag, a Release and a CHANGELOG.md entry marked 👀 “what to check in the play-test”.

boot-check

Tests green, types clean, build passed — and the screen is black. Headless Chrome loads the built app and fails if it doesn't start.

TODO as a living backlog

Play-test → the bug goes in right away → “bugs first, polish later”. No roadmap on paper.

The boot-check story: a temporal dead zone (TDZ) in main.ts. No unit test loads main.ts, so everything was green while the game wouldn't start. Since then the check is mandatory for any change that touches main. ~2 min.

who really wrote the collision code

Where the agent got it wrong — and how we caught it

“An invisible wall in the middle of an ordinary road”
play-test bug report, Paris, Île de la Cité, v0.148.1

  • The agent added a debug readout to the pause screen: solid: quay@1.3m
  • The cause: the quay only had a lower bound. 1593 walls → 25
  • The same class of bug, for the third time

Takeaway

The invariant went straight into TODO: solid ⇒ visible.

The agent doesn't remember the last session. The repo does: AGENTS.md, TODO, CHANGELOG, tests.

A human spotted the bug by eye; the agent built a diagnostic tool and found the cause. The important part: to keep it from happening a fourth time, the lesson has to be written where the agent will read it. ~2 min.

github.com/kryadov/claude-remote-vm-dev

A typical loop: start a session, give it a task, close the laptop. In the morning, VS Code Remote-SSH for the diffs, rd-attach to answer the agent's questions, then a merge request. You can show the rd-tui gif from the README. ~2.5 min.

why a VM and not just a cloud agent

For corporate development

Perimeter

Code and tokens never leave the company network. The VM is the isolation boundary, so the agent can run docker compose without worry.

Secrets

Provider credentials live in a 0600 file. Only the provider's name goes into tmux, so nothing shows up in ps.

Bedrock gotchas

Without pinned models, the opus alias quietly falls back to a smaller model. WebSearch isn't available there.

One idempotent bootstrap script. Spec on August 15, a working version two weeks later. Built with an agent, too.

For those who hear “we're not allowed in the cloud”: this is how you get L6 inside the perimeter. ~1.5 min.

“security included”

What to give an agent overnight: npm audit 9 → 0

race-the-city v0.149.1, October 15, 2026, a single commit:

  • 9 vulnerabilities → 0: 2 critical, 3 high, 4 moderate, all in the dev/build toolchain
  • Vite 5 → 8, Vitest 2 → 5: RCE in tinypool, path traversal in @vitest/mocker, a leak in the esbuild dev server
  • A breaking change fixed along the way: Vite 8 builds with Rolldown, manualChunks → codeSplitting
  • boot-check got BOOT_CHECK_PORT so parallel checkouts don't collide

Why it's the perfect overnight task

  • A clear finish line: npm audit = 0
  • A safety net: tests + boot-check
  • Boring for a human, not for an agent

In the CHANGELOG: 👀 “nothing should look different”.

This is where the subtitle pays off. The backlog and security updates are the best background work for an agent: the definition of done is formal, the check is automatic, and the agent gets through major upgrades with breaking changes on its own. In the morning you look at a green CI and one line in the changelog. ~2 min.

My part: one decision

  • gather the reports into one plan
  • see that the tasks are independent
  • say “in parallel”

Claude Code: everything else

  • 7 subagents in a single message
  • 7 worktrees, 7 branches
  • tests in each, 7 merges one at a time
I asked for parallelism myself, but the tool did the rest. The main session is the orchestrator: it calls the Agent tool with isolation: worktree, and Claude Code gives each subagent its own git worktree and a worktree-agent-<id> branch. A subagent starts with a clean context, does its task, runs the tests and returns a short report. The orchestrator merges the branches one at a time. The order comes from superpowers: dispatching-parallel-agents, subagent-driven-development. Models by role: in itffm Opus 5/5.5 co-authored 53 commits (specs, plans, the hard parts), Sonnet 5 — 280 (execution). The expensive model thinks, the fast one does. ~2.5 min.

One primitive — git worktree — and two orchestrators

I wrote the worktree-per-session setup. How many agents, and on what — a human decides.

L7

itffm, Claude Code

me → “in parallel”
agent → Agent(isolation: worktree) ×7
agent → merge ×7

The tool creates the worktrees. How to split the work — the agent decides; I just approve.

Where the agent runs no longer matters:

your own VMtmux + systemd
cloudclaude.ai/code
phonea remote for any of them
The main point: I didn't build L7, the tool gave it to me. My job on this rung is to make tasks independent and verifiable: a plan, tests, boot-check, a CLAUDE.md with shared rules for all seven. I started sessions from both the computer and the phone — it varied. Where it breaks: hot files (main.ts, CHANGELOG) cause merge conflicts; shared resources like ports (hence BOOT_CHECK_PORT in Race the City, “so parallel checkouts don't collide”); every subagent starts from scratch and pays for context in tokens; reviewing seven branches is still on a human. ~2 min.

the new bottleneck

What tests don't catch

  • Oyster mushrooms rendered as flat pancakes: the generator put the stem in the center
  • Chimeras: a 25 cm cap on a 6 cm stem
  • 243 mushrooms × 5 meshes → a thousand draw calls; even the headless browser froze

The fix is a tool for looking with your own eyes: npm run silhouette-sheet, every species' silhouette on a single sheet.

The bottleneck moved

From “write the code” to “check the result”.

Agents write faster than I can look. Review and visual checks are now the human's main job.

All three examples are recorded in section 0 of the design doc. No unit test would have caught them; it took a pair of eyes. That's why it pays to build tools that compress checking: a contact sheet, boot-check, a debug readout on the pause screen. ~2 min.

back to the self-imposed limits

Medium or x-high: it depends on the kind of task

kind of taskexamplehypothesis
Executing a plana task from the plan with tests already writtenmedium ≈ x-high, and GLM/Kimi are often enough
More of the sameone more car, one more mushroom species in YAMLmedium ≈ x-high
Diagnosisthe invisible wall on the quay, third time roundx-high pays off
Spec and planendless world, quests, a minex-high and an expensive model

The better the spec and tests, the less effort execution needs. You pay once, at the planning stage.

This is where my own observations go: on which tasks the difference between medium and x-high was noticeable, and on which it wasn't. How to check: the same task, two runs, compared by tests, boot-check and by eye. Same logic in itffm: Opus writes the plan, Sonnet executes it. ~2 min.

what you can take to your team tomorrow

Five rules

  • Spec before code. The agent executes a plan. An empty prompt breeds improvisation
  • The contract lives in the repo. AGENTS.md / CLAUDE.md, invariants, known pitfalls. The agent forgets; the repo remembers
  • Check that it boots, not just that tests pass. boot-check catches what green CI misses
  • One agent, one worktree. Without it, parallelism turns into merge conflicts
  • Tools for your eyes. Compress review: contact sheets, readouts, 👀 in the changelog
The key slide for practitioners. ~1.5 min.
